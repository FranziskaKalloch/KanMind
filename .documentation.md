Im zweiten Schritt werden die Beziehungen hergestellt.

## Board

- title                 string
- owner                 ForeignKey auf User
- members               ManyToManyField auf user
- tasks                 ForeignKey

Es gibt nur einen owner pro Board, aber der User kann mehrere Boards besitzen.

Ein Board kann mehrere Members haben, ein Member kann auch mehrere Boards haben: ManyToMany

## Tasks

- board                 als ForeignKey auf Board
- title                 string
- description           string
- status                Auswahl ('to-do', 'in-progress', 'review', oder 'done')
- priority              Auswahl ('low', 'medium', 'high')
- assignee              ForeignKey auf User definieren
- reviewer              ForeignKey auf User definieren
- due_date              Datum

Es kann nur einen Reviewer auf einem Task geben, aber der Reviewer kann mehrere Tasks haben, bei denen er reviewt, also 1:n (FOREIGNKEY)

Assignee kann ebenfalls nur einer pro Tasks sein, aber der Assignee kann mehrere Tasks haben, also 1:n (FOREIGNKEY)

Priority ist eine Auswahl (low, medium, high)

status: ebenfalls eine Choice

board: eine Task kann nur einem Board zugeordnet sein, aber ein Board kann mehrere Tasks haben: 1:n (FOREIGNKEY)

## Comment

- created_at            Datum
- author                ForeignKey
- content               string
- task                  ForeignKey

Ein Comment kann nur zu einem Task zugeordnet werden, aber es können mehrere Comments in einem Task sein, also -> 1:n (FOREIGNKEY)

Ein User kann mehrere Comments erstellen. Ein Comment kan nur von einem User erstellt werden, also 1:n (FOREIGNKEY)

Bei 1:n immer bei der 1 den ForeignKey setzen

## related_name

Beispiel: assignee = models.ForeignKey(settings.AUTH_USER_MODEL, on_delete=models.CASCADE, related_name="tasks")

Ein related_name="tasks" erlaubt es mir, von einem User aus direkt auf alle seine Posts zuzugreifen mit z.B. user.tasks.all()

### get_queryset() "Welche Datenbankeinträge kommen für diese Anfrage infrage?"

Ist eine vorhandene Methode in DRF von den generischen Views (zb ListAPIView).

1. Der Benutzer fragt: "Zeig mir meine Boards"
2. Die View muss bestimmen, welche Boards er sehen darf
3. Dafür ruft DRF die Methode get_queryset() auf
4. Die Methode sucht die Boards, bei denen der Benutzer entweder Owner oder Member ist, und gibt diese zurück

Ein QuerySet ist eine Auswahl von Datenbankeinträgen, daher get_queryset - "gib mir diese Auswahl"

Reihenfolge:
Anfrage -> View wählt Boards aus -> Serializer bereitet deren Daten auf -> Antwort
