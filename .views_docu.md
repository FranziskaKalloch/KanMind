# Views im Django REST Framework – Gegenüberstellung

Alle DRF-Views bauen aufeinander auf:

```description
django.views.View
 └── APIView                      (rest_framework.views)
      └── GenericAPIView          (rest_framework.generics)
           ├── + Mixins → CreateAPIView, ListAPIView, RetrieveUpdateDestroyAPIView, ...
           └── + Mixins + ViewSetMixin → GenericViewSet → ModelViewSet
```

Je weiter unten, desto mehr passiert automatisch – aber desto weniger Kontrolle hat man „im Sichtfeld".

---

## Kurzvergleich

| | `APIView` | `GenericAPIView` (pur) | Concrete Generics (`CreateAPIView`, `ListCreateAPIView` …) | `ModelViewSet` |

|---|---|---|---|---|
| **Basisklasse** | `View` | `APIView` | `GenericAPIView` + Mixins | `GenericViewSet` + alle Mixins |
| **Handler-Methoden** | `get`, `post`, `put`, `patch`, `delete` selbst schreiben | `get`/`post` … selbst schreiben | bereits vorhanden (`get`, `post` …) | **Actions**: `list`, `create`, `retrieve`, `update`, `partial_update`, `destroy` |
| **Queryset / Serializer** | selbst holen | über `queryset`, `serializer_class` | über `queryset`, `serializer_class` | über `queryset`, `serializer_class` |
| **Objekt laden (404)** | selbst (`get_object_or_404`) | `get_object()` | automatisch | automatisch |
| **Validierung** | selbst (`is_valid()`) | selbst | automatisch | automatisch |
| **Speichern** | selbst (`serializer.save()`) | selbst | automatisch (`perform_create` …) | automatisch (`perform_create` …) |
| **Response + Statuscode** | selbst | selbst | automatisch (200/201/204) | automatisch (200/201/204) |
| **Pagination / Filter** | nein | nur manuell nutzbar | automatisch bei List | automatisch bei List |
| **URLs** | `path()` pro View | `path()` pro View | `path()` pro View | **Router** erzeugt URLs |
| **Kontrolle** | maximal | hoch | mittel | gering (dafür wenig Code) |
| **Typischer Einsatz** | Sonderlogik, kein Model-CRUD | selten pur | Einzelne Endpunkte mit Standardverhalten | Komplettes CRUD für eine Ressource |

---

## Was DRF in *jeder* View automatisch macht (ab `APIView`)

Diese Dinge kommen von `APIView` und gelten für alle Varianten:

- `request` wird zu einem DRF-`Request` (`request.data`, `request.query_params`, Parser für JSON/Form)
- Rückgabe muss eine DRF-`Response` sein → Renderer wandelt in JSON um (Content Negotiation)
- Authentifizierung (`authentication_classes`) und Berechtigungen (`permission_classes`), Throttling
- Exceptions (`ValidationError`, `NotFound`, `PermissionDenied` …) werden in saubere Fehler-Responses mit Statuscode umgewandelt
- Nicht implementierte HTTP-Methoden → `405 Method Not Allowed`

### Ablauf eines Requests (APIView)

```description
dispatch()
 ├── initialize_request()      → Django-Request → DRF-Request
 ├── initial()
 │    ├── perform_authentication()   → request.user
 │    ├── check_permissions()        → has_permission()
 │    └── check_throttles()
 ├── Handler aufrufen          → get() / post() / put() / patch() / delete()
 ├── (bei Exception) handle_exception()
 └── finalize_response()       → Renderer, Header
```

Hinweis: `has_object_permission()` wird **nicht** automatisch aufgerufen – nur über `self.check_object_permissions(request, obj)`. `GenericAPIView.get_object()` macht das für dich.

## 1. `APIView`

**Was sie tut:** Die Basis aller DRF-Views. Du schreibst pro HTTP-Methode eine Methode und machst alles selbst.

**Automatisch:** Request/Response-Wrapping, Auth, Permissions, Throttling, Exception-Handling, 405 bei fehlender Methode.

**Nicht automatisch:** Queryset, Objekt laden, 404, Serializer erzeugen, Validieren, Speichern, Statuscode, Pagination, Filter.

**Aufgerufene Methoden:**

| HTTP | Methode |

|---|---|
| GET | `get(self, request, ...)` |
| POST | `post(self, request, ...)` |
| PUT | `put(self, request, ...)` |
| PATCH | `patch(self, request, ...)` |
| DELETE | `delete(self, request, ...)` |

```python
class BoardListView(APIView):
    permission_classes = [IsAuthenticated]

    def get(self, request):
        boards = Board.objects.filter(members=request.user)
        serializer = BoardSerializer(boards, many=True)
        return Response(serializer.data)

    def post(self, request):
        serializer = BoardSerializer(data=request.data)
        serializer.is_valid(raise_exception=True)
        serializer.save(owner=request.user)
        return Response(serializer.data, status=status.HTTP_201_CREATED)


class BoardDetailView(APIView):
    def get(self, request, pk):
        board = get_object_or_404(Board, pk=pk)
        self.check_object_permissions(request, board)   # manuell!
        return Response(BoardSerializer(board).data)

    def delete(self, request, pk):
        board = get_object_or_404(Board, pk=pk)
        board.delete()
        return Response(status=status.HTTP_204_NO_CONTENT)
```

**Wann nutzen:** Endpunkte, die nicht zu einem Model passen (Login, Statistik, Dashboard, Aktionen wie „Task zuweisen"), oder wenn du den Ablauf voll steuern willst.

## 2. `GenericAPIView` (die „einfache" Generic-Basis)

**Was sie tut:** `APIView` + Helfer für Queryset und Serializer. Allein macht sie noch kein CRUD – du rufst die Helfer selbst auf. Meist wird sie mit Mixins kombiniert.

**Zusätzliche Attribute:** `queryset`, `serializer_class`, `lookup_field` (Default `pk`), `lookup_url_kwarg`, `filter_backends`, `pagination_class`.

**Helfer-Methoden:**

| Methode | Aufgabe |

|---|---|
| `get_queryset()` | liefert das Queryset (überschreiben für Filter nach User) |
| `get_object()` | `filter_queryset` → Objekt per `lookup_field` holen → 404 → `check_object_permissions` |
| `get_serializer_class()` | welche Serializer-Klasse (überschreiben z. B. je nach Aktion) |
| `get_serializer(...)` | Instanz mit `context` (request, view, format) |
| `get_serializer_context()` | Context-Dict für den Serializer |
| `filter_queryset(qs)` | wendet `filter_backends` an |
| `paginate_queryset(qs)` / `get_paginated_response(data)` | Pagination |

**Automatisch:** alles von `APIView` + Hilfsmethoden (nur wenn du sie aufrufst).

**Nicht automatisch:** Die Handler `get`/`post` … fehlen → ohne eigene Methoden ist es `405`.

```python
class BoardView(GenericAPIView):
    queryset = Board.objects.all()
    serializer_class = BoardSerializer

    def get(self, request, pk):
        board = self.get_object()                 # 404 + Object-Permissions inklusive
        return Response(self.get_serializer(board).data)
```

## 3. Concrete Generic Views (`CreateAPIView`, `ListAPIView`, …)

**Was sie tut:** `GenericAPIView` + passende Mixin(s). Die HTTP-Methode ist bereits an die Mixin-Action gebunden. Du setzt nur `queryset` und `serializer_class`.

| Klasse | HTTP → Mixin-Methode |

|---|---|
| `ListAPIView` | GET → `list()` |
| `CreateAPIView` | POST → `create()` |
| `RetrieveAPIView` | GET → `retrieve()` |
| `UpdateAPIView` | PUT → `update()`, PATCH → `partial_update()` |
| `DestroyAPIView` | DELETE → `destroy()` |
| `ListCreateAPIView` | GET → `list()`, POST → `create()` |
| `RetrieveUpdateAPIView` | GET, PUT, PATCH |
| `RetrieveDestroyAPIView` | GET, DELETE |
| `RetrieveUpdateDestroyAPIView` | GET, PUT, PATCH, DELETE |

### Ablauf am Beispiel `CreateAPIView` (POST)

```decription
dispatch() → initial() (Auth, Permissions, Throttle)
 └── post(request)                     # ruft nur self.create() auf
      └── CreateModelMixin.create()
           ├── get_serializer(data=request.data)
           ├── serializer.is_valid(raise_exception=True)   → 400 bei Fehler
           ├── perform_create(serializer)                  → serializer.save()
           ├── get_success_headers()
           └── Response(serializer.data, status=201)
```

### Ablauf `ListAPIView` (GET)

```decription
get() → list()
 ├── filter_queryset(get_queryset())      → Filter-Backends
 ├── paginate_queryset()                  → falls Pagination aktiv
 ├── get_serializer(..., many=True)
 └── Response(serializer.data)            → 200
```

### Ablauf `RetrieveUpdateDestroyAPIView`

```description
GET    → retrieve():       get_object() → get_serializer(obj) → 200
PUT    → update():         get_object() → get_serializer(obj, data, partial=False)
                           → is_valid → perform_update() → 200
PATCH  → partial_update(): wie update, aber partial=True
DELETE → destroy():        get_object() → perform_destroy(obj) → obj.delete() → 204
```

**Automatisch:** Serializer bauen, validieren, 400 bei Fehlern, 404 bei fehlendem Objekt, Object-Permissions, Speichern/Löschen, Statuscodes (200/201/204), Pagination und Filter bei List.

**Nicht automatisch:** Setzen von Feldern, die nicht vom Client kommen (z. B. `owner=request.user`) → dafür `perform_create()` überschreiben. Einschränkung auf „nur eigene Objekte" → `get_queryset()` überschreiben. URLs müssen manuell eingetragen werden. Andere HTTP-Methoden (z. B. DELETE bei `CreateAPIView`) → `405`.

**Typische Hooks zum Überschreiben:**

| Hook | Zweck |

|---|---|
| `get_queryset()` | Daten einschränken (nur eigene Boards) |
| `get_serializer_class()` | anderen Serializer je Methode |
| `perform_create(serializer)` | zusätzliche Felder beim Speichern |
| `perform_update(serializer)` | Logik beim Update |
| `perform_destroy(instance)` | Soft-Delete, Aufräumen |
| `get_serializer_context()` | Extra-Daten für den Serializer |

```python
class BoardListCreateView(ListCreateAPIView):
    serializer_class = BoardSerializer
    permission_classes = [IsAuthenticated]

    def get_queryset(self):
        return Board.objects.filter(members=self.request.user)

    def perform_create(self, serializer):
        serializer.save(owner=self.request.user)


class BoardDetailView(RetrieveUpdateDestroyAPIView):
    queryset = Board.objects.all()
    serializer_class = BoardSerializer
    permission_classes = [IsAuthenticated, IsBoardMember]
```

**Wann nutzen:** Standard-Endpunkte mit klar definiertem Verhalten, bei denen du pro URL festlegen willst, was erlaubt ist.

## 4. `ModelViewSet`

**Was sie tut:** Eine Klasse für **alle** CRUD-Operationen einer Ressource. Besteht aus `GenericViewSet` + `Create`, `Retrieve`, `Update`, `Destroy`, `List`-Mixin. Der Unterschied zu den Generics: Es gibt keine `get`/`post`-Methoden, sondern **Actions**. Das Mapping HTTP → Action übernimmt der **Router**.

**Mapping durch den Router:**

| URL | HTTP | Action |

|---|---|---|
| `/boards/` | GET | `list` |
| `/boards/` | POST | `create` |
| `/boards/{pk}/` | GET | `retrieve` |
| `/boards/{pk}/` | PUT | `update` |
| `/boards/{pk}/` | PATCH | `partial_update` |
| `/boards/{pk}/` | DELETE | `destroy` |

### Ablauf

```description
Router erzeugt URLs + mappt {'get': 'list', 'post': 'create'} usw.
 └── ViewSetMixin.as_view(actions) → setzt self.action
      └── dispatch() → initial() (Auth, Permissions, Throttle)
           └── Handler = Action-Methode (z. B. self.create)
                └── wie bei den Generics: get_serializer → is_valid → perform_create → Response
```

`self.action` enthält den Namen der aktuellen Action (`'list'`, `'create'`, …) → damit lassen sich Serializer und Permissions pro Action steuern:

```python
class BoardViewSet(ModelViewSet):
    queryset = Board.objects.all()

    def get_serializer_class(self):
        if self.action == 'list':
            return BoardListSerializer
        return BoardDetailSerializer

    def get_permissions(self):
        if self.action in ('update', 'partial_update', 'destroy'):
            return [IsAuthenticated(), IsBoardOwner()]
        return [IsAuthenticated()]

    def perform_create(self, serializer):
        serializer.save(owner=self.request.user)
```

```python
# urls.py
router = DefaultRouter()
router.register('boards', BoardViewSet, basename='board')
urlpatterns = router.urls
```

**Zusätzliche Endpunkte mit `@action`:**

```python
@action(detail=True, methods=['post'])      # POST /boards/{pk}/archive/
def archive(self, request, pk=None):
    board = self.get_object()
    board.archive()
    return Response(status=status.HTTP_204_NO_CONTENT)
```

**Automatisch:** alles wie bei den Concrete Generics, zusätzlich **URL-Erzeugung** (Router, inkl. API-Root-Übersicht), Action-Zuordnung, `self.action`.

**Nicht automatisch:** Einschränkung auf eigene Objekte, Setzen von Feldern wie `owner`, unterschiedliche Rechte je Action – alles über Hooks (`get_queryset`, `perform_*`, `get_permissions`, `get_serializer_class`). Will man nur Teile von CRUD, vererbt man statt `ModelViewSet` von `GenericViewSet` + gewünschten Mixins (oder `ReadOnlyModelViewSet`).

**Wann nutzen:** Klassisches vollständiges CRUD für eine Ressource, wenig Code gewünscht, Router akzeptabel.

## Welche Methode wird wann aufgerufen? (Übersicht)

| Request | APIView | Concrete Generic (z. B. `ListCreateAPIView`) | ModelViewSet |

|---|---|---|---|
| `GET /x/` | `get()` | `get()` → `list()` | `list()` |
| `POST /x/` | `post()` | `post()` → `create()` → `perform_create()` | `create()` → `perform_create()` |
| `GET /x/1/` | `get()` | `get()` → `retrieve()` → `get_object()` | `retrieve()` → `get_object()` |
| `PUT /x/1/` | `put()` | `put()` → `update()` → `perform_update()` | `update()` → `perform_update()` |
| `PATCH /x/1/` | `patch()` | `patch()` → `partial_update()` → `update(partial=True)` | `partial_update()` → `perform_update()` |
| `DELETE /x/1/` | `delete()` | `delete()` → `destroy()` → `perform_destroy()` | `destroy()` → `perform_destroy()` |

Davor läuft immer: `dispatch()` → `initial()` → Authentifizierung → `check_permissions()` → Throttling.

---

## Entscheidungshilfe

- **Eigene Logik, kein reines Model-CRUD** (Login, Registrierung, Statistiken, Aktionen) → `APIView`
- **Einzelne Standard-Endpunkte, volle URL-Kontrolle** → Concrete Generics (`ListCreateAPIView`, `RetrieveUpdateDestroyAPIView` …)
- **Vollständiges CRUD, möglichst wenig Code** → `ModelViewSet` + Router
- **Nur Lesen** → `ReadOnlyModelViewSet` bzw. `ListAPIView` / `RetrieveAPIView`

Faustregel: Die Concrete Generics und das `ModelViewSet` machen **dasselbe**, nur anders verpackt – bei den Generics wählt man Klassen pro URL, beim ViewSet bündelt der Router alles in einer Klasse.
